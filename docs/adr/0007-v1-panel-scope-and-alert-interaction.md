# ADR-0007: V1 面板显示范围 + Alert 形态与点击交互（自绘置顶窗+通知，点击统一开面板，终端跳转降级为行内 best-effort）

- status: accepted
- date: 2026-07-15

## 背景

ADR-0004 定了"托盘 + Alert"的呈现骨架，并给 Alert 点击定了一套按 session 数量分叉的行为（1 个 Waiting → 直接聚焦终端；≥2 个 → 开面板）。但它没细化三件事：**面板到底显示哪些 session**、**Alert 具体是什么形态**、**点击到底怎么走**。2026-07-15 的 grilling 会话就这三点逐一压测，并用本机真实数据与 Spike B 的结论校准。相关事实：

- 本机 Claude 历史会话文件 2220 个、此刻真正在跑约 9 个——面板不可能按历史全列。
- **实测约束**：Waiting/Idle 的会话一旦停下就不再写文件，因此"按文件 mtime 最近有没有变"来判是否上榜是错的——一个"已经等你 30 分钟"的会话会因文件不动而掉榜，而它恰是最该显示的。
- **macOS 事实**：没有公开 API 能让 App 查询"用户是否开着专注模式 / 我这条通知有没有被压制"，所以"检测到被压制再切换兜底方案"这类条件分叉不可实现。
- **Spike B 事实**（见 `docs/research/2026-07-15-v1-feasibility-spikes.md`）：会话文件里没有 tty/pid，session→终端窗口只能按 cwd 猜；对用户在用的 Ghostty 只暴露 working directory、不暴露 tty，同 cwd 多 session 时会跳不准。终端聚焦是"分终端 best-effort"，不是统一可靠能力。
- **Observer 约束**（ADR-0002）：WhoNeedsMe 不负责启动 Agent CLI；没有直接 Session 级信号时，OS 进程与会话文件通常只能用 Provider + cwd（工作目录）关联。同一 cwd 既可能有历史 Session，也可能同时存在多个活 Session，因此系统需要内部处理关联置信度，但不能把"不确定"包装成面板上的用户警告。

## 决策

1. **面板显示范围以"进程存活"为准，不做历史时间窗**：有直接 Session-PID 关联时，一个 Session 在榜当且仅当其 CLI 进程还活着（Working / Waiting / Idle 都在）；进程一死判 Ended，在榜短暂 grace 后掉出。只有 Provider + cwd 可用时，若该组发现 N 个活进程，面板最多选择最近活跃的 N 个候选 Session，避免一个活进程把同目录历史 Session 全部带上榜。文件活动时间只用于候选排序，**不单独作为存活判据**。排序 **Waiting（Needs You）置顶 → Working → Idle → 刚结束**。**Elapsed = 进入当前状态的时长**；对 Waiting 即"已经等了你多久"。
2. **关联置信度只在系统内部使用**：主面板只展示筛选后的活跃 Session，不显示"关联不确定"、"低精度"或类似削弱信任的标签。推断关联可以支持列表展示；Needs You 必须来自该 Session 的直接状态信号，不能仅凭同 cwd 有活进程推断；依赖精确进程的操作无法确认目标时走既有降级路径。
3. **Alert 形态 = 自绘置顶窗（主）+ 原生通知（辅），两条无条件都发**：Needs You 触发时，一个 **Tauri 自绘置顶小窗**必弹——它可靠必达、不吃通知权限、不被专注模式/勿扰压制、停留到用户处理、承载点击逻辑、跨平台一致；同时**附带发一条原生系统通知**，只为触达锁屏 / 其他 Space / 通知中心历史。两条各管不同触达场景（窗管当下这块屏、通知管你不在这块屏时），**不做"检测被压制再兜底"的条件分叉**（该检测不可实现）。自绘窗遵循 ADR-0004 的克制工具感，且不抢键盘焦点。Alert 的合并/去重规则沿用 ADR-0004（至多一个、多 session 合并为"N 个 session 在等你"）。
4. **点击交互统一为"开面板列表"，修订 ADR-0004 的分叉点击**：点击（托盘图标 / Alert 窗）一律打开面板，把所有在榜 session 用列表 + 状态呈现。**终端聚焦跳转从"单 session 直接跳"降级为"面板内每行的一个 best-effort 行内动作"**——用户在列表里点某一行 → 尽力跳去该 session 的终端窗口（能精确跳则跳，跳不准则退化为把对应终端 App 带到前台）。终端跳转**不再在任何必经路径上**。因此 ADR-0004 后果里"单 session 场景窗口聚焦跳转是 In Scope"改写为"窗口聚焦跳转是面板内 best-effort 行内动作"；"终端聚焦 adapter"从核心架构维度缩为一个可选的行内功能。

## 理由

- **进程存活 vs 时间窗**：进程存活是"这是我此刻真开着的会话"的最干净信号，天然把列表收敛到一把（≈开着的终端数），且**唯一能让长时间 Waiting 的会话留在榜上**——这正是产品的核心用例。时间窗/mtime 新鲜度会把最该提醒的会话过滤掉，被否。
- **内部置信度 vs 用户警告**：关联置信度是采集层选择候选和执行降级所需的内部事实，不是用户的任务。把"关联不确定"显示在 Session 行上，只会把实现限制翻译成产品不可靠感；主界面应直接交付筛选后的结果。宁缺毋滥仍由 Needs You 的直接信号门槛保证，而不是靠警告文案转嫁风险。
- **自绘窗 vs 原生通知**：产品的整个价值是"别让在等的 agent 被忽略"，而原生通知最致命的失效模式恰是"专注模式下被压制"——用户埋头干活（常开专注模式）时正是最需要提醒的时刻；加上通知权限可被拒 = 核心功能静默失效。自绘窗不受这两者约束，是唯一能兑现"必达"的形态。原生通知不被丢弃，是因为它能覆盖自绘窗够不到的锁屏/跨 Space/历史场景——两者互补而非冗余。被否备选：纯原生通知（会被勿扰吞、点击分叉逻辑弱）；纯自绘窗（锁屏/跨屏时看不到）。
- **点击统一开面板 vs 分叉直跳终端**：用户明确表达"点击就想一眼看到所有 session 的列表与状态"；而 Spike B 证明"直接跳终端"对其 Ghostty 是 best-effort、可能跳错。把点击统一成可靠的"开列表"、把不可靠的跳终端降级为行内 best-effort 动作，使主交互路径永远可靠，同时保留跳终端的便利而不让它的不确定性污染主流程。这也让 V1 不必先啃下"终端聚焦 adapter"这块硬骨头。

## 后果

- 面板需要可靠的**进程存活计数**与候选筛选：同一 Provider + cwd 下 N 个活进程最多带 N 个最近活跃 Session 上榜，不能把同目录历史 Session 全部映射成存活。
- 关联置信度保留在内部诊断数据，不进入 Session 行文案；只有直接 Session 状态信号能触发 Needs You，依赖精确进程的动作沿用 best-effort 降级。
- PRD（Issue #2）的 US#21/#22（Alert 点击按数量分叉）与 Out of Scope 里关于窗口聚焦的措辞需按本 ADR 改写：点击统一开面板；终端跳转为面板内 best-effort 行内动作。
- Alert 实现为"自绘窗 + 原生通知"两套发送，自绘窗需实现为不抢键盘焦点的置顶窗口。
- 终端聚焦跳转作为行内 best-effort 动作，其"分终端适配"（Terminal.app/iTerm2 走 tty 精确、Ghostty 走 cwd、其余降级到把 App 带前台）留给实现时按覆盖面推进，不作为 V1 的硬验收项。
- DESIGN.md（ADR-0004 已列为 UI readiness 硬要求）需覆盖：面板列表 + 托盘 + 自绘 Alert 窗三者的视觉与交互；仍是 UI 票进入 ready-for-agent 前的前置 Task。
