# ADR-0004: V1 呈现形态定为托盘常驻 + Alert 弹窗，不做灵动岛/拟人化吉祥物

- status: accepted
- date: 2026-07-14

## 背景

ADR-0001 定了产品形态是 Tauri 托盘应用，但只笼统提到"有人等待时高亮"，没有细化"以什么形式让用户实际注意到"。在拆 Issue #4（托盘图标 + 会话列表面板 UI）时，用户提出顾虑：单纯托盘图标变化可能不会被注意到。市场调研中最像的两个正面竞品都在托盘之外加了更抓眼球的呈现层——Agent Island 用 macOS 灵动岛/顶栏 + Windows 原生浮动 widget，looppulse 用托盘触发的 CleanMyMac 风格滑出面板。由此展开一轮烤问，覆盖是否拟人化、常驻呈现载体、"只读"边界的精确含义、以及触发提醒的聚合/点击行为。

## 决策

- **不做拟人化吉祥物**，保持克制工具感的视觉语言。
- **V1 常驻呈现用托盘图标**，不做灵动岛/顶栏这类依赖 macOS 私有 AppKit API 且 Windows 无对应物的呈现，留给 V2 视需要再评估。
- **Needs You 从 false 变为 true 时触发一个前台 Alert**，弥补托盘图标本身不够抓眼球的问题；同一时刻至多一个 Alert，多个 session 同时进入 Waiting 时合并显示（"N 个 session 在等你"），不逐个弹出。
- **精确"只读"边界**：WhoNeedsMe 不代替用户向任何 Provider 输入内容（不发消息、不批准权限、不做任何 Agent 侧操作）；但窗口聚焦跳转（把对应终端带到前台）不算违反只读。
- **Alert 点击行为按 session 数量分叉**：对应 1 个 Waiting session 时，点击直接聚焦跳转到该 session 的终端窗口；对应 ≥2 个时，点击打开 WhoNeedsMe 自己的面板列表，由用户自己挑选。

## 理由

- 拟人化吉祥物与已确立的"沉默 hook""宁缺毋滥"这套克制产品哲学有张力；市场调研中真正跑出规模的两个项目（claude-hud、CodexBar）也都是纯功能性 UI，没有拟人化角色。
- 灵动岛/顶栏方案技术上依赖 macOS 私有 API，和 ADR-0001 选 Tauri 而非 Swift 的初衷（不被平台锁死）有拧巴；Windows 又完全没有对应概念。用"触发时弹出 Alert"能达到同样的"抓眼球"效果，且是纯 Tauri 能力范围内、跨平台一致的方案——这也是 Agent Island 自己实际在用的组合拳（顶栏常驻 + 前台 alarm 弹窗一起上），说明"抓眼球"不必然等于"必须做灵动岛"。
- Alert 合并/去重是"Needs You 聚合规则"（托盘只给一个信号，不逐个刷屏）在弹窗层面的延伸，避免多 session 同时等待时弹窗轰炸。
- "只读"精确定义为"不代替用户输入"而非"零交互"，是因为纯通知、点了没反应的提醒实际抓手价值有限——市场调研里表现好的竞品（Agent Island、squawk、agent-monitor）通知点击后都会直接带你去对应终端。窗口聚焦不涉及向 Agent 输入任何东西，风险性质和"代替用户批准权限"完全不同，不该被同一个"只读"边界一刀切掉。
- 被否备选：灵动岛/顶栏作为 V1 首选——被否是因为技术锁定与 Windows 空白的代价现在就要背，而"托盘 + Alert"已经能验证核心价值；灵动岛留作 V2 差异化增强，不是被永久放弃。

## 后果

- Issue #2（PRD）Out of Scope 里"点击 session 跳转到对应终端窗口……V1 不做交互式控制"这条需要收窄改写——单 session 场景下的窗口聚焦跳转现在是 In Scope。
- Issue #4（托盘图标 + 会话列表面板 UI）的范围需要扩展为"托盘图标 + Alert 弹窗 + 面板列表"三件套，且仍然卡在 `DESIGN.md` 缺失这个 readiness 硬性要求上。
- 灵动岛/顶栏、拟人化呈现作为 V2 备选方向记录在案，不在 V1 实现范围内。
